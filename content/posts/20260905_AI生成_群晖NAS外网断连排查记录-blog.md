> 本文由 AI 辅助排查并整理。现象：群晖 NAS 外网访问断连；耗时半天；最终定位出双重根因（运营商 CGNAT + 光猫模式变更），打客服电话开通公网 IP 解决。以下是完整的排查逻辑链。

## 问题定义

- 现象：DDNS 域名解析正常，浏览器访问 DSM 的 5000/5001 端口持续超时
- 背景：当天早上在路由器上配置过 IPv6，期间 NAS 曾「通了一会儿又断」
- 已知条件：端口转发规则自配置以来未改动过；今天之前外网访问一直正常

一个关键的初步观察：失败模式是 **Connection timed out（超时）**，而非 **Connection refused（拒绝）**：

| 失败模式 | 含义 | 指向 |
|---|---|---|
| refused | 包到达了目标，端口无人监听 | 服务问题 |
| timeout | 包在路径中被静默丢弃 | 链路上有设备在拦 |

timeout 优先怀疑链路，而非服务。

## 排查时间线

每一步都遵循同一逻辑：**提出假设 → 找证据 → 证实或排除 → 缩小包围圈**。

### 第 1 步：排除本地网络

用外部多节点拨测服务（check-host.net）从四个海外节点探测 `IP:5000`：

```
德国 / 伊朗 / 意大利 / 哈萨克斯坦
→ 全部 Connection timed out
```

四个方向的独立观察点结论一致，排除「我这边网络不好」。同时说明：**任何人从外面都进不来**，问题定位到家庭入口。

### 第 2 步：判定 NAS 本体状态

两个独立证据：

1. `dig AAAA` 发现域名存在 IPv6 记录，TTL 仅 30 秒且一小时内前缀变过一次、网卡后缀不变——这条记录只有 NAS 在线才会持续上报。**NAS 活着**
2. DSM 信息中心：内网服务 HTTP 200、千兆全双工、IPv4/IPv6 双栈正常、DDNS 状态绿灯

顺带解释了「早上通一会儿又断」：宽带 IPv6 前缀在漂移（运营商分配的前缀在重拨后更换），通了 = 前缀刚下发、记录刚更新；断了 = 前缀又漂了。这个现象本身是第 5 步的重要伏笔。

### 第 3 步：验证 DDNS 是否说谎

借家庭内网另一台机器执行：

```bash
curl -4 -s http://ip.3322.net          # 宽带当前出口 IP
dig +short A <我的DDNS域名>             # DDNS 记录的 IP
dig +short AAAA <我的DDNS域名>          # DDNS 记录的 IPv6
```

三者交叉比对：DDNS 记录与真实出口一致。**DDNS 无罪**。注意这里必须借内网视角——外部的测试机(本机挂着半死的 Clash 代理)所有本地测试结论都不可信，外部拨测 + 内网视角交叉验证是本次排查能走对路的关键方法论。

### 第 4 步：验证保底通道

QuickConnect 中继正常登录。该通道走群晖官方服务器中继，不依赖家庭任何端口映射和 IP，确认应急可用。这一步不影响诊断，但决定了后续可以放心大胆地改配置。

### 第 5 步：traceroute 定罪

```bash
traceroute -n -m 5 -w 2 223.5.5.5
```

```
1  192.168.3.1     ← 自家路由器
2  192.168.1.1     ← 第二层网关（光猫）
3  100.66.92.1     ← 实锤：落在 100.64.0.0/10
```

`100.64.0.0/10` 是 RFC 6598 规定的运营商级 NAT（Carrier-Grade NAT）专用网段。第三跳落在这里，意味着：

- 本宽带本次拨号获得的是**运营商共享出口 IP**，不是真公网地址
- 外部对 5000 端口的入站连接，在运营商 CGNAT 网关处就被丢弃——**端口转发规则根本没有机会被执行**
- 这解释了第 1 步「全球四节点全部超时」，也解释了「配置没动过却失效」：电信动态公网本质是抽奖，每次 PPPoE 重拨重新分配，掉进 CGNAT 池属于随机事件。早上折腾路由器触发重拨，恰好抽中

同时第 2 跳暴露了第二个问题：**光猫工作在路由模式**，家庭网络实际是双层 NAT（光猫 NAT 套路由器 NAT）。这与早上配置 IPv6 的时间点吻合——光猫疑似从桥接被切到路由模式，IPv6 由此打通（对应「早上通了一会儿」），但 IPv4 入站链在这层被截断。

### 第 6 步：重拨验证 + 收尾

触发 PPPoE 重拨：出口 IP 更新为新的公网地址，CGNAT 排除。但外部拨测依然超时——印证第 5 步的推断：**光猫路由模式这层门还关着**。

## ✅ 最终解法（重点）

> **致电运营商（10000）申请开通公网 IP。**
>
> 话术一句话：**「家里装了 NAS 和监控，需要外网访问，帮我开通公网 IP。」**
>
> 免费下发 → 重拨 → DDNS 自动跟进 → 原有端口转发规则直接复活，**全程十几分钟**。
>
> 前提提醒：公网 IP 开通后，若光猫仍是路由模式（双层 NAT），还需在光猫管理页做 DMZ 或端口映射指向内层路由器，IPv4 入站才真正打通。

解决路径回顾：重拨抽奖只能碰运气，电话开通公网 IP 才是确定性的解。

## 根因总结

```
外网访问断连
├── 根因一：PPPoE 重拨后掉入 CGNAT 共享池
│    └── 证据：traceroute 第 3 跳 100.66.92.1 ∈ 100.64.0.0/10
└── 根因二：光猫从桥接被切为路由模式，IPv4 入站链在第一层 NAT 截断
     └── 证据：双层网关（192.168.3.1 → 192.168.1.1）+ 重拨后仍超时
```

两个根因都「无声」：配置没有任何变化，规则一条没丢，但环境变了，规则就全部失效。

## 最终访问架构

| 通道 | 依赖 | 状态 |
|---|---|---|
| 公网 IPv4 + DDNS | 运营商下发真公网 IP + 端口转发 | 主力（本次修复） |
| QuickConnect 中继 | 群晖官方服务器 | 保底（全程未中断） |
| IPv6 + DDNS | 宽带 IPv6 + DDNS 记录准确 | 待启用 |

## 可复用经验

**1. CGNAT 一条命令定罪**

```bash
traceroute -n -m 5 -w 2 223.5.5.5
```

第三跳落在 `100.64.0.0/10` 即实锤。先要公网 IP，再查别的——顺序反了会白折腾路由器。

**2. IPv6 临时地址会让 DDNS 指错门**

同一网卡可能并存两个全局 IPv6 地址：固定地址（MAC 经 EUI-64 生成）与临时地址（隐私扩展，定期轮换）。DDNS 若上报了临时地址，前缀一漂移就指向不存在的门。本次实测：固定地址外部可达、临时地址不可达，而 DDNS 恰好指向后者。治本方案是在系统层面关闭临时地址生成。

**3. 「配置没动却失效」= 优先怀疑链路环境**

PPPoE 重拨换 IP、动态公网掉 CGNAT、光猫/路由器模式变更，都会无声吃掉端口转发规则。**配置不变不等于环境不变**，排障时链路层证据（traceroute）优先于配置层检查。

**4. 测试机被污染时，交叉验证是唯一出路**

本机代理处于半开状态（TUN 网卡在、端口无监听）时，所有本地测试都可能失真。此时用「外部拨测点 + 家庭内网另一台机器」两个视角交叉验证，任何单一视角的结论都不可单独采信。

```bash
# 外部多点拨测（排除本地网络干扰）：check-host.net → TCP port
```
